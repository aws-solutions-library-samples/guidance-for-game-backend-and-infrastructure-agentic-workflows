# Bounded-autonomy runtime closes the replay and dispatch-evidence chain

Issue #439 now provides a reachable evaluator-to-executor path for hash-bound v2 capacity operations while preserving the v1 human-approval path. The final commit closes the settled-result replay failure by accepting only a contract-valid E3 terminal result bound to the exact operation and derived logical action before live reservation verification. It also makes `dispatched` an atomic successor of a matching `dispatch_requested` record and requires both records at fresh execution. The remaining evaluator, policy, gate, reservation, expiry, workflow, routing, and provider-isolation acceptance points are implemented and covered by the operations regression suite.

Watch for: **confirmed** terminal replay is the only pre-live-reservation shortcut, and malformed, mismatched, or nonterminal documents cannot take it; they proceed to dispatch-audit and live verification.

**Verdict**: APPROVED

## High-level view

The v2 executor first reloads the immutable bundle and derives the logical action from the operation id and prepared hash. It may return an existing E3 result before checking live reservation ownership, but only after the frozen result contract and both identifiers validate; accepted replay performs no Describe, provider write, verifier call, or settlement.

Dispatch proof is now a two-record chain. The store creates `dispatched` through a transaction whose condition requires the matching `dispatch_requested` execution name, and the executor independently loads both records and requires their operation ids and execution names to agree before a fresh execution can verify or write.

The evaluator entrypoint reads a closed event, reloads a succeeded observation under the configured workspace, loads the exact configured policy id, version, and hash, and reads the configured rolling-window state. Dispatch intersects static `operate`, a separate fresh autonomy switch, the E4 dispatch gate, and durable E4 intent; execution repeats the E4 checks and re-runs the v2 verifier at the current clock immediately before the provider write.

Reservation state uses revision-fenced DynamoDB transactions with immutable lifecycle audit records, an active-owner index, bounded lease, generation fencing, conservative settlement, and opportunistic expired-owner recovery. The Standard workflow and executor boundary remain identifier-only, and the evaluator has no GameLift or Lambda-invoke client.

## Exact E3 terminal replay before live reservation ownership

`execute_reloaded` reloads and classifies the server-owned v2 bundle before deriving the action id from `(operation_id, prepared_hash)` (`backend/src/operations/execute/executor_entry.py:264-372`). `_attempt_terminal_replay` then reads through the autonomous `ExecutorService`'s narrow E3 result accessor, validates the document against `gamelift-capacity-execution-result`, and requires exact operation-id and logical-action-id equality (`executor_entry.py:456-496`; `executor_service.py:254-268`). The frozen result schema admits only `SUCCEEDED`, `RECONCILED`, `FAILED`, and `HUMAN_RECONCILIATION_REQUIRED`, so a nonterminal outcome cannot satisfy the contract.

An accepted result returns before dispatch-audit lookup, v2 verification, E3 lease acquisition, Describe, provider write, and reservation settlement. This ordering restores idempotent replay after the first attempt has settled generation 1. A missing loader or result, malformed contract, wrong operation id, wrong action id, or nonterminal outcome returns `None`; `execute_reloaded` then requires dispatch evidence and runs the unchanged live verifier/write path.

## Atomic requested-to-dispatched evidence

`record_dispatch_requested` remains an immutable conditional record written before StartExecution. `record_dispatched` now uses one `TransactWriteItems` request containing a `ConditionCheck` for the exact request row and execution name plus an immutable `Put` for the dispatched row (`backend/src/operations/autonomy_runtime/store.py:1159-1228`). A missing predecessor, crossed execution name, or differing existing dispatched record fails closed. A byte-identical dispatched replay reconciles without rewriting evidence.

Fresh v2 execution does not trust the dispatched marker alone. `_require_dispatched_audit` loads both phases, validates their phase and operation fields, and requires the same non-empty execution name (`backend/src/operations/execute/executor_entry.py:498-538`). This check runs before the autonomous verifier and provider path; a terminal E3 replay is already an immutable executor-produced terminal fact and needs no new write authorization.

## Trusted evaluator assembly and exact policy selection

The module-level Lambda handler and lazy bootstrap are present (`backend/src/operations/autonomy_runtime/evaluator_entry.py:751-910`). The event parser accepts exactly `observation_operation_id`, `desired`, `minimum`, and `maximum`; tenant, workspace, policy, authority, automation principal, enrollment, and correlation remain server-owned. The runtime accepts only a succeeded durable observation, projects it through the frozen autonomy contract, and revalidates the assembled decision and operation binding (`backend/src/operations/autonomy_runtime/service.py:160-231`).

`DynamoDbAutonomyPolicyLoader` addresses the configured id/version key, compares the document's id, version, and hash to all three configured pins, and revalidates the frozen policy contract (`evaluator_entry.py:304-426`). The evaluator bootstrap constructs DynamoDB and Step Functions clients plus local AppConfig readers; static scans and client-construction tests found no GameLift client, Lambda-invoke client, or provider-write method in the evaluator modules.

## Current owner recovery, generation fencing, and audit settlement

Reserve persists the reservation, advances the exact window revision, sets `in_flight`, records the active operation owner, and appends `autonomy_reserved` in one transaction (`backend/src/operations/autonomy_runtime/store.py:626-745`). A concurrent identical loser re-reads and converges only when action, state, and generation match. Distinct operations, stale revisions, and mismatched bindings remain conflicts.

The production window loader calls `sweep_state` before `current`, and `sweep_state` resolves the single active owner without scanning (`evaluator_entry.py:429-459`; `store.py:910-940`). Reclaim occurs only after the bounded lease deadline, releases only concurrency, advances the revision, marks the reservation `reclaimed`, increments its generation, and appends the lifecycle audit atomically. The stale holder then fails both ownership and settlement checks.

Settlement requires the matching action and generation, releases the slot while retaining budget and frequency, persists the bounded terminal token, and writes `autonomy_settled` in the same transaction (`store.py:747-824`). Conditional ambiguity is resolved by re-reading both reservation and window state; success is reported only when the record is settled and `in_flight` is zero.

## Last-current-time gate and sole provider writer

`AutonomyExecutionVerifier.verify` revalidates operation identity, the complete #438 binding, `APPROVED_AUTONOMOUS` authority, configured identities, deployment authority, decision/window freshness, the fresh separate switch, and live reservation ownership (`backend/src/operations/autonomy_execution_verifier.py:252-454`). After the pre-write Describe, `build_pre_write_reverify_hook` reloads the bundle and runs that verifier again using its current clock, requires the same logical action, then repeats the separate-switch and generation-1 reservation checks (`executor_entry.py:374-429`). `ExecutorService` runs this hook after the second E4 execute-phase check and immediately before its single `update_capacity` call (`backend/src/operations/execute/executor_service.py:318-353`).

The runtime builds distinct v1 and v2 `ExecutorService` instances. The v1 instance keeps its original verifier and no autonomy hook; the v2 instance carries a verifier sentinel that rejects accidental v1 use and shares only the established E3 write core (`executor_entry.py:648-759`). The existing CloudFormation workflow is explicitly `STANDARD`, passes only `operation_id`, and invokes the executor without an automatic retry (`infrastructure/cloudformation/07-operations-execution.yaml:666-712`).
