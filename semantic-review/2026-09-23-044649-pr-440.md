# E5 autonomy deployment still leaves live proof and restoration gaps

PR #440 adds the optional E5 evaluator plane, cross-stack activation wrappers, and a command-backed deployed shakedown on top of the existing 06/07/08 operations stacks. `cc77cda` repairs the authenticated observation request, GameLift location API, E4/E5 flag folding, and unknown-state handling identified in the `7794bcd` review. Four blocking data-flow issues remain, including two findings that the earlier review raised but the final revision did not wire through. Static template, shell, IAM, and cost checks pass, but they do not exercise these seams.

Watch for: **[confirmed]** the succeeded 06 observation ID is discarded before evaluation; **[confirmed]** the immediate inverse is denied by the same cooldown and anti-oscillation state the shakedown just established; **[confirmed]** activation never compares 07 table/KMS/tenant/workspace parameters with 06; **[confirmed]** CloudTrail attribution is neither correlated to the current write nor bound to the deployed executor role.

**Verdict**: NEEDS_CHANGES

## High-level view

The 06 client now uses HTTPS, carries the bearer only in the header, sends `fleet_id` plus `idempotency_token`, and polls the real status route. **[confirmed]** `CommandTransport._observe` returns that succeeded ID only to the check response, while `_closed_event` uses the separately supplied `CommandAdapterConfig.observation_operation_id`. The evaluation therefore does not consume the observation that the shakedown just established.

The lifecycle verifies a rate-limit denial and immediately asks the same evaluator for the inverse. **[confirmed]** the forward reservation sets `last_write_epoch_seconds`, increments `writes_in_window`, and records the increase direction; cooldown, frequency, and anti-oscillation checks also apply to the inverse. The three-attempt, two-second cleanup loop cannot outwait the repository's valid 300-second cooldown and 600-second reversal interval.

The wrapper binds 07's state-machine ARN, fleet, and audience and binds supplied E5 values to 06 and 08. **[confirmed]** it does not read 07 `OperationsTableName`, `OperationsKmsKeyArn`, `TenantId`, or `WorkspaceId`; Phase 2 preserves them with `UsePreviousValue=true`. The exact comparison helper exists only in a unit test.

The dispatch evidence reads the execution and DynamoDB keys. **[confirmed]** CloudTrail is queried only by fleet resource name, the newest result's `Username` is copied without checking event name or time, and the harness compares it to the literal `executor`. The 07 stack exports `ExecutorRoleArn`, but the adapter never receives or compares it.

## Succeeded 06 observation never becomes the evaluator coordinate

**[confirmed]** `observe_succeeded_observation_id` returns the operation ID only after terminal `succeeded` status (`e5_command_adapter.py:304-377`). `CommandTransport._observe` places that ID into its check response (`:1071-1076`) without updating lifecycle state. Forward, retry, inverse, and forced evaluations call `_closed_event`, which reads the original configured value at `:1084-1099`; `_build_command_adapter` initializes it from the CLI's pre-supplied `--observation-id` at `e5_shakedown.py:772-817`.

```text
06 POST + poll -> newly succeeded obs_new -> trusted check response -> discarded
CLI --observation-id -> adapter config obs_old -> every evaluator event
```

The `7794bcd` review raised this handoff gap. The new test verifies HTTP and polling in isolation but never asserts that the returned ID reaches `invoke_evaluate`. Bind the succeeded ID into the lifecycle before evaluation, and obtain another succeeded observation after the forward write if the inverse must evaluate observed `desired=1`.

## Limit proof prevents the required inverse and bounded cleanup

**[confirmed]** `_next_reserved` increments `writes_in_window`, sets `last_write_epoch_seconds`, and records `last_change_direction` (`autonomy_runtime/store.py:262-283`). The evaluator denies writes inside `min_seconds_between_writes` and opposite-direction changes inside the anti-oscillation interval (`contracts/autonomy.py:865-886`). The shipped valid policy fixture uses 300 seconds for cooldown and 600 seconds for reversal.

The shakedown proves an immediate retry denial at `e5_shakedown.py:428-438`, then invokes `down` without waiting or using a restoration path at `:546-551`. If denied, `_confirm_capacity_zero` retries three times with two-second sleeps (`:612-626`) before disabling autonomy. The summary fails, but the fleet can remain at `desired=1`, contrary to the documented guaranteed return to zero.

The fake applies cooldown only when `direction == "up"` (`test_operations_e5_shakedown_unit.py:132`), while the evaluator applies limits to both directions. Use a separately authorized compensation path that explicitly permits restoration, or wait for and verify a policy-admissible inverse with a fresh observation. Do not claim teardown success until capacity is confirmed zero.

## 07 persistence and identity coordinates bypass exact activation binding

**[confirmed]** the wrapper reads 07 only for `ExecutionStateMachineArn`, `EnrolledFleetId`, and `TrustedAudience` (`deploy-operations-autonomy.sh:429-472`). It reads the 06 table, CMK, tenant, workspace, and audience and compares them only with supplied E5 values (`:484-547`). It never reads the corresponding 07 parameters even though 07 injects all four into the executor.

Phase 2 preserves every non-autonomy 07 parameter with `UsePreviousValue=true` (`:1036-1069`). A 07 stack bound to a different table or identity scope can therefore enter `AutonomyMode=operate` while 09 writes its bundle and reservation to 06. `verify_activation_binding` models the required comparison at `e5_command_adapter.py:913-958`, but repository search finds only unit-test callers.

The `7794bcd` review also raised this gap. Compare the four live 07 parameters byte-for-byte with 06 before the first mutation, and add wrapper-level mismatch tests.

## CloudTrail evidence does not identify the current executor write

**[confirmed]** `lookup_write_attribution` filters only on `ResourceName=<fleet-id>` (`e5_command_adapter.py:512-518`). `_dispatch_evidence` selects `Events[0]` and copies its flattened `Username` (`:1194-1201`) without checking `EventName == UpdateFleetCapacity`, an execution-bound time range, the target location, or `userIdentity.sessionContext.sessionIssuer.arn`. The harness accepts only the literal `executor` (`e5_shakedown.py:393-406`).

CloudTrail results are newest-first and can contain other activity for the fleet. The literal is not bound to the deployment; 07 exports `ExecutorRoleArn` at `07-operations-execution.yaml:1263-1268`, but `CommandAdapterConfig` has no expected executor identity. The check can attribute an unrelated event or reject the correct role.

Bind the 07 role ARN, parse `CloudTrailEvent`, filter the current `UpdateFleetCapacity` event by a bounded execution window and target, and require the assumed-role session issuer ARN to equal the bound role. AWS documents the ordering and full event field here: https://docs.aws.amazon.com/awscloudtrail/latest/userguide/view-cloudtrail-events-cli.html.
