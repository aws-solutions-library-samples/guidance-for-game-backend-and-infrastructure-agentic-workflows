# E5 bounded-autonomy runtime remains unreachable and breaks the v1 path

The issue #439 branch adds immutable bundle persistence, exact v2 verification, identifier-only Step Functions input, and immediate pre-write controls around the existing executor. At exact head `8c88352`, all four known reservation defects remain. Independent review also found that the evaluator has no callable Lambda or trusted-input loader, and enabling v2 replaces the v1 service with a verifier that always raises. Autonomous dispatch lacks a durable `dispatched` transition, and the AppConfig switch treats ambiguous naive timestamps as UTC.

Watch for: **confirmed** permanent reservation wedges after crashes; **confirmed** concurrent same-operation replay conflicts; **confirmed** fabricated settlement success and absent settlement audit; **confirmed** evaluator dead code; **confirmed** v1 failure when autonomy is configured; **confirmed** missing autonomous dispatch state; **confirmed** naive AppConfig timestamps treated as UTC.

**Verdict**: NEEDS_CHANGES

## High-level view

The reservation store uses an unbounded Boolean in-flight slot. It has no deadline or generation, maps every reserve condition loss to conflict, assumes every settle condition loss means success, and stores no terminal reason or lifecycle audit event.

`evaluator_entry.py` resolves strict settings and constructs narrow clients, stores, and gates, but stops at returning `AutonomyRuntimeHandler`. No Lambda `handler` constructs `AutonomyRuntimeInputs`, and no production caller loads the policy, observation, window state, requested capacity, authority, principal, correlation, or evaluation time from trusted sources.

The v2 verifier and pre-write hook retain exact policy/evidence/state bindings and keep GameLift access in the executor. Runtime construction then selects the autonomous `ExecutorService` for both paths, so v1 reaches `ExecutionVerifierUnused` whenever autonomy is enabled.

The autonomous handler persists, reserves, gates, and starts Step Functions without recording `dispatched`. Terminal execution records later name `dispatched` as the previous state without proving that transition.

The separate AppConfig switch uses a closed document and fresh extension reads, but `_instant` assigns UTC to offset-less values instead of denying them.

## Reservation ownership cannot recover or converge

**Confirmed:** `reserve` records only `operation_id`, `logical_action_id`, `state_id`, and `settled`, then requires `in_flight == 0` (`backend/src/operations/autonomy_runtime/store.py:484-550`). No lease deadline or generation exists. A crash after reservation leaves `in_flight == 1` permanently, and `require` cannot fence a superseded holder (`store.py:562-566`). Add a bounded deadline and monotonically increasing generation, reclaim only after expiry, and fence `require` and `settle` on the generation. Keep TTL off durable window and audit records.

**Confirmed:** the pre-read at `store.py:490-495` handles only serial replay. Two identical callers can both observe no record; the transaction loser reaches `store.py:552-557`, which returns `CONFLICT` for every conditional failure. Re-read after condition loss and converge to `RESERVED` only when the stored operation and logical action exactly match. Preserve `CONFLICT` for a different action or lost window fence.

**Confirmed:** `settle` has independent window and reservation conditions, but every conditional failure returns `RESERVED` (`store.py:568-612`). A revision move or ownership loss can therefore report successful settlement while the slot remains held. Re-read both records, prove the exact reservation is settled or released before returning success, and return conflict/unavailable otherwise. A generation fence must prevent a reclaimed holder from releasing its successor.

**Confirmed:** the `terminal` argument at `store.py:568` is discarded. The update only writes `settled = true` (`store.py:595-601`), and neither transaction appends an atomic audit event. Persist a closed terminal reason and settlement time, with reservation and settlement ledger events in the same transactions as their accounting changes.

## Evaluator bootstrap has no invocable path

**Confirmed:** the evaluator exposes settings resolution, `DynamoDbWindowStateLoader`, and `build_evaluator_handler`, but no module-level Lambda `handler`; the builder only returns `AutonomyRuntimeHandler` (`backend/src/operations/autonomy_runtime/evaluator_entry.py:228-315`). No production caller uses the builder. `AutonomyRuntimeInputs` is constructed only in tests, and the configured policy id/version/hash never loads or validates a policy here. A runtime probe confirmed `hasattr(evaluator_entry, "handler") == False`.

Add a closed trigger contract and Lambda handler that loads the code-owned policy, canonical observation, and current window state from trusted stores, derives authority/principal/correlation/time server-side, and calls `dispatch`. The event must not carry policy, limits, identity, credentials, or executable content.

## Autonomy configuration replaces the human-approved executor service

**Confirmed:** the v1 branch calls `runtime.service.execute` (`backend/src/operations/execute/executor_entry.py:226`). `_build_runtime` assigns `autonomy_service` to that slot when v2 is configured (`executor_entry.py:365-366`), and that service uses `ExecutionVerifierUnused` (`executor_entry.py:460-476`). A valid v1 runtime probe reproduced `RuntimeError: the autonomous executor service does not run the v1 approval verifier`.

The tests manually supply one fake service that implements both methods, so they do not exercise this composition. Keep separate human and autonomous services. Route v1 only through the unchanged `ExecutionVerifier` service and v2 only through `execute_verified` with the autonomy pre-write hook.

## Autonomous execution claims a dispatch transition that never occurred

**Confirmed:** `AutonomyRuntimeHandler.dispatch` persists, reserves, gates, and starts the workflow but writes no operation state (`backend/src/operations/autonomy_runtime/handler.py:116-179`). No autonomous code owns `STATE#current` or a `dispatched` transition. The executor passes `expected_state="dispatched"` (`backend/src/operations/execute/executor_service.py:508`), while `DynamoDbExecutionStore` merely copies it into `previous_state` (`backend/src/operations/execute/execution_store.py:216-238`).

Record an atomic dispatch ownership/state transition before StartExecution, tied to the operation and reservation fence. Terminal recording must condition on that durable state rather than label an unverified predecessor.

## AppConfig switch accepts ambiguous timestamps

**Confirmed:** `_instant` accepts timestamps without offsets and applies `timezone.utc`, despite the validator's normalized-UTC contract (`backend/src/operations/autonomy_switch.py:120-125,250-258`). A runtime probe showed naive `issued_at` and `not_after` values enabling autonomy. Reject parsed values without `tzinfo` or `utcoffset()`, and cover the denial.

## Boundaries to preserve and missing composition tests

Provider separation remains explicit: the evaluator creates only DynamoDB and Step Functions SDK clients (`evaluator_entry.py:259-263`) and reads AppConfig through localhost, while the executor alone creates GameLift (`executor_entry.py:301-303`). The v2 verifier retains deterministic bindings, exact deployed identities and authority, decision/window freshness, the separate switch, and reservation ownership. The pre-write hook repeats switch and ownership checks after the E4 execute gate. Fixes must preserve these boundaries.

The no-AWS review run passed 133 focused tests. Missing coverage includes concurrent reserve loss, crash reclaim, ambiguous settle, an actual evaluator invocation, `_build_runtime` with autonomy enabled plus v1 input, durable autonomous dispatch state, and offset-less AppConfig timestamps.
